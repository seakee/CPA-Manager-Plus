## Overview

v1.14.6 is a maintenance patch after v1.14.5, limited to three already-merged fixes: Codex workspace spend-control limits (#935 / #938), retained monitoring data protection during usage archive cleanup (#939 / #945), and cache-token double counting for otherwise-unknown events with strict CPA v2 accounting evidence (#941 / #946).

This release does not introduce new features, polling, or timers, and it does not change CPA management APIs, credential privileges, or the SQLite schema.

## Highlights

### Fixes

- **Codex workspace spend control (#935 / #938):** Correctly interpret structured `spend_control.individual_limit` while retaining legacy scalar and persisted browser quota-cache compatibility. Preserve budget, used/remaining amounts, units, time windows, and reset evidence. An exhausted spend-control limit remains a limited/quota-risk state, even if standard 5-hour or weekly quotas have headroom.
- Explain zero-budget `0 / 0` cases as a workspace-budget restriction rather than a misleading generic “100% used” limit. Suggest reviewing the workspace budget only when complete spend-control evidence is the sole limitation; preserve the existing quota-refresh recommendation when other quota signals compete. No background provider probing or polling is added.
- **Archive cleanup integrity (#939 / #945):** Before each bounded raw-event deletion batch, verify that the corresponding retained Monitoring projection rows exist and have matching timestamps. Repair only missing/mismatched rows from still-live raw data and verify the handoff within the same SQLite transaction; fail closed and roll back if integrity cannot be established.
- On cleanup resume, verify retained projections for events deleted earlier in the same run before allowing more deletion. This prevents future losses of this kind but **does not reconstruct already permanently deleted raw history**.
- **CPA v2 canonical cache accounting (#941 / #946):** For previously unclassified events, use canonical cache semantics only when CPA v2 `accounting_version=2` and `token_breakdown.schema_version=2` provide a complete, internally consistent breakdown across input, cache, output, reasoning, and total tokens. This prevents counting cache-read tokens twice.
- Preserve existing explicit and known provider/executor/model precedence; incomplete, ambiguous, unknown-version or inconsistent evidence keeps the previous fallback. Standard JSONL imports/exports distinguish upstream-declared cache modes from CPAMP-derived accounting hints rather than promoting derived values into raw upstream evidence.
- Automatically reconcile eligible historical online `usage_events` through the existing accounting-semantics migration path and rebuild affected usage/pricing aggregates. No manual SQLite edits or offline cleanup command are needed.

## Upgrade Notes

- **A normal upgrade and restart is sufficient.** There is no SQLite schema or configuration format migration, but eligible historical events undergo an automatic accounting-semantics correction and corresponding usage/cost rollups may change.
- Keep a consistent database and archive backup before upgrading. If exact pre-upgrade historical accounting must be restored after the automatic rewrite, restore the matching pre-upgrade database/archive backup instead of manually reversing derived fields.
- Strict canonical cache accounting is used only when complete CPA v2 evidence exists; other events preserve previous compatibility behavior. The minimum CPA baseline for full Muse / Meta functionality remains **v7.3.4+**.
- Archive deletion may incur a small bounded verification cost; cleanup fails closed if retained material coverage cannot be proven.
- No new background polling, timers, or manual maintenance commands are introduced.
