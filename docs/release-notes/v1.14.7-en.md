## Overview

v1.14.7 is a 1.x maintenance release after v1.14.6. It includes five already-merged fixes and performance improvements: a SQLite covering index for long-window latency analytics (#960), removal of history-sized candidate reads from the quota-snapshot writer hot path (#981), the Antigravity Hub client-identity compatibility fix (#986), unified non-blocking background refresh behavior across v1 views (#987), and inclusion of the first request after a Codex five-hour rollover (#991).

This release adds no new 1.x feature, does not change CPA management APIs, credential privileges, the SQLite schema, or configuration formats, and introduces no new polling jobs or timers.

## Highlights

### Fixes

- **Background refresh behavior (#987):** Loaded credentials, configuration, OAuth rules, Dashboard data, logs, plugins, System data, provider model discovery, Usage Analytics, and action-candidate views now retain the current successful snapshot while revalidating within the same data scope instead of reverting to full loading, blank content, or a false empty state.
- A transient revalidation failure keeps the last successful content visible with lightweight failure feedback, while a successful empty response is treated as a loaded empty snapshot. Connection, provider, credential, and capability scope changes invalidate stale data, late responses, and captured destructive actions.
- Loaded credential configuration remains visible but read-only after a reload failure and becomes editable again after a successful retry. Log reading position, plugin iframes, and loaded charts remain stable during ordinary refreshes.
- **Antigravity quota compatibility (#986):** Replace the obsolete antigravity/cli/1.0.13 management-request identity with the Hub identity used by current CPA so Cloud Code no longer truncates retrieveUserQuotaSummary because of the old-client floor. Gemini weekly and five-hour quota buckets are available again without changing endpoints, polling, or quota parsing semantics.
- **First Codex request after a five-hour rollover (#991):** When the previous cycle has ended but a request starts a few seconds before the response headers establish the new scheduled cycle start, that confirmed request now belongs to the new cycle's actual interval rather than being omitted from both cycles. Scheduled boundaries remain unchanged and the request is not double counted.
- **Quota Snapshot write performance (#981):** Remove the history-sized candidate query and sort from the writer hot path while leaving cross-request boundary canonicalization in the existing lifecycle repository. External quota APIs, displayed semantics, and persistence formats are unchanged.

### Performance

- **Long-window latency analytics (#960):** Add a (timestamp_ms, latency_ms, ttft_ms) covering index through the existing deferred/offline derived-index lifecycle while retaining production SQL, the timestamp index, and exact percentile definitions.
- On a warmed synthetic 3.2M-event database, the 30-day raw SQL scan median fell from about 3.77 seconds to 0.43 seconds. The exact 120-day percentile SQL remains sorting-bound, improving from roughly 49 seconds to 25 seconds in that experiment. These figures describe the measured index boundary and are not an end-to-end guarantee for every deployment.
- The index adds modest disk and write overhead. Complex provider/model/account filters can still require table reads, and very long exact-percentile windows remain a future optimization area; this maintenance release does not expand into pre-aggregation or percentile-algorithm redesign.

## Upgrade Notes

- **A normal upgrade and restart is sufficient for all correctness fixes in v1.14.7.** There is no SQLite schema or configuration-format migration, so migration_required remains false.
- On an existing non-empty usage.sqlite, the new latency covering index from #960 follows the existing deferred/offline maintenance lifecycle. Skipping that maintenance does not prevent Manager Server from starting or serving requests; it only postpones the index's performance benefit.
- To build the new index for an existing large database, stop Manager Server, run the existing offline maintenance command:
  cpa-manager-plus cleanup-derived --db-path <database-path>
  and restart Manager Server afterward. Docker deployments should use the repository's existing stopped-service offline cleanup-derived procedure.
- compact-usage **does not replace** cleanup-derived; it serves the usage compaction/cleanup path and does not complete this deferred derived-index build. Keep a consistent database backup before offline database maintenance.
- Fresh empty databases continue to create the relevant indexes through the existing post-listen maintenance path and do not require the separate offline step.
- #991 applies to newly reconciled Codex five-hour rollovers after upgrade; already-persisted historical cycle boundaries are not automatically backfilled or rewritten.
- The minimum CPA baseline for full Muse / Meta functionality remains **v7.3.4+**; #986 does not raise the minimum CPA version.
